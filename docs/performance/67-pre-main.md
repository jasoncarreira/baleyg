## PR #99 round4 POSIX SQLite lock-retention repair (exact-head review and both CI runs pending)

- **Verified pre-fix loss, not a flaky fixture:** both Ubuntu jobs on `a964952` returned HTTP 500 for Java `/api/index` POST; original Claude reproduced `SQLITE_IOERR_RDLOCK` extended code 2314 during queue COMMIT. On POSIX, `close()` of **any** separate fd for a file releases all process fcntl locks on that inode, even locks SQLite holds through other connections. The old `requests.db` `OpenOptions` check closed a fresh fd on every queue read/write. `verify_index_file` and `IndexFileWitness` independently did the same for live `index.db`. Two processes could then write simultaneously, lose a committed row or read beneath a writer.
- **Deterministic red→green across both DBs:** A holds `BEGIN IMMEDIATE` and an existing durable ACK on `requests.db`; a second thread invokes `request_by_id`, and a child process tries `BEGIN IMMEDIATE` plus a write. Before repair, the child **committed** despite A's live transaction. Parallel tests reproduced this for direct `verify_index_file(index.db)` and `IndexFileWitness::open`/drop. After repair, each child gets BUSY, A COMMIT succeeds, and the prior queue ACK and index publication pin remain intact. These are real cross-process locks, not a mocked error.
- **Never close a live SQLite check fd:** one process-wide, single-flight witness cache retains the `O_NOFOLLOW` file handle from first open through process exit. A cache hit still checks the current pathname, owner, 0600 mode, nlink and dev/inode; a replaced inode gets a new retained handle without closing the old one. `verify_index_file` validates the exact SQLite header with positional reads from its retained fd; `IndexFileWitness` holds an `Arc` of that fd. New staged `index.db` creation also registers its handle **before** SQLite opens or rename can expose it. Capacity is explicitly bounded to 4096 retained handles; exhaustion refuses **before open** and never evicts a potentially live inode. Queue existing-only reads and root/path/claim fences are unchanged.
- **Should-fix follow-up in this head:** API errors inspect allowlisted causes across the full error chain, so a wrapped `storage_busy`/`root_changed` maps correctly. SQLite `IOERR` (including `IOERR_RDLOCK`) has 500 precedence and is never relabeled 409 or retried as contention. Verified daemon-leader same-seq busy requeue uses a 250 ms reader backoff rather than recapturing every 20 ms. An ambiguous post-COMMIT CLI error now says the ACK remains durable/unfinished for the next verified leader; regression exercises queued Q2 behind Q1 or Q2 itself running and successor FIFO completion. T04 cancellation, root fences, observational Status and report-only GC remain unchanged.
