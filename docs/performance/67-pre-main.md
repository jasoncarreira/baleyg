## PR #99 round2 original-Claude fixes (new exact-head rereview and CI pending)

- **T04 cancellation, red before fix:** a browser-owned B ahead of CLI C became terminal `failed/index_failed` when CLI Ctrl-C happened during B's capture. Now the CLI exits **before** `record_and_finish_request`; B remains `running` without error/revision, C remains `queued`, and a new verified leader reclaims B then C in durable FIFO. The CLI's own accepted running row also remains unfinished on Ctrl-C. No waiting client can terminally fail another client's ACK.
- **Externally repaired daemon, red before fix:** after a real CLI repaired corrupt index.db to r1 and released its leader lock, the stale daemon returned `recovery_required: corruption/obsolete marker authority not verified` on every 20 ms tick; a real browser POST stayed queued and Status failed. The daemon now authenticates a valid **same-root** publication with an existing-only use guard, `O_NOFOLLOW` pathname/inode witness, and its recovery baseline/pin from the **same read-only SQLite transaction**. It adopts Ready without reusing stale EX authority. With CLI leadership held, the daemon follows without publication and Status reads r1. Once that owner exits, a verified daemon leader reconciles once before Status; a new browser ACK then finishes under verified leadership. Missing/busy/corrupt observations fail closed with bounded exceptional retry, and root replacement bypasses backoff for fencing. No Status handler writes storage.
- **Three minor findings:** an existing-only read of a creator's `requests.db` at `user_version=0` returns `storage_busy` rather than falsely claiming an incompatible initialized schema; neither the file nor schema changes. Follower takeover uses the unchanged durable FIFO head's persisted options, and a failed capture may terminally fail only that exact authenticated head after verified claim and unchanged root/pin checks—not a different client with daemon-default inputs. A stale claim cannot occupy the successor's cached completion slot or complete a row that a new leader reclaimed (`request claim changed`); only that new verified claim finishes it.
- **Linux CI fixture:** prior `e9442f4` Ubuntu jobs timed out on the one serve-ingress health check after its banner. The test had closed the child stderr pipe at the first banner line. It now keeps stderr open in a private temporary file through shutdown, preserves the 15-second HTTP readiness assertion, and reports only allowlisted exit/HTTP/stderr categories on failure. The exact CLI test passes locally; the new exact-head Ubuntu/macOS CI rerun remains a merge gate. This is a fixture repair, not a weaker `/healthz` contract.

## PR #99 queue repair probes (round1, with round2 correction)

A follower only marks a capture failure `index_failed` after it owns and verifies the leader fence, rechecks the current root and unchanged publication pin, and claims the FIFO head. A real unreadable source records that terminal state once rather than recapturing every 20 ms. A fresh Ready `requests.db` remains absent after current/by-ID reads and the queue directory is unchanged. `/api/jobs/current` excludes older rows from a replaced root.

Under an independent shared reader, a real browser POST Q1 and concurrently accepted CLI Q2 have durable seq1/seq2 while queued. After release, the daemon publishes new-generation r1/r2 in FIFO order; the CLI may have a stale pre-repair disposition, so it reopens **only the same verified root and already-existing index** before reporting completed Q2. A request admitted **after** a recovery capture cannot claim that earlier pin. The first round1 Ctrl-C test expected `index_failed`; round2 T04 corrected that contract. Ctrl-C stops the waiter but leaves any accepted running row for a verified new leader to reclaim, never terminally fails that row.

Owner-required post-ACK refresh hardening has a deterministic two-case race probe at the exact old existence-check/SQLite-open boundary. The old helper failed both: same-UID removal let `Store::open` bootstrap a new index; byte-identical 0600 inode replacement claimed stale success. The new helper uses only an existing SH use lock, same verified root identity, `O_NOFOLLOW` inode/path witness and an in-memory Store whose SQLite connection opens **read-only existing** bytes. It runs the normal recovery-baseline validation; pathname/inode and root fences are checked before and after. Removal leaves `index.db` absent and the accepted queue unchanged; restoring the saved old file yields the exact old generation/revision. Replacement is refused with unchanged pin/queue bytes. No `Store::open` initialization path is reachable. Corrupt, busy or missing publication fails closed without turning an accepted queue row into false `done`.

A separate test process committed a request pin while its durable row was `running`, recorded both facts, then exited with code 37 **before** the terminal queue write. The parent reopens the same storage and observes the published pin plus still-running row, then a new verified leader reconciles and reclaims that FIFO head to `done` at a later pin. In-process cached terminal-write retry avoids duplicate publication when that holder survives; **process death in this gap may cause another publication**. No across-process exactly-once guarantee is claimed. This is distinct from the older injected same-process completion-failure tests.

Unchanged Serve is the narrowly measured optimization here; an explicit no-change browser indexing command is still a durable request and takes its normal validated path.
